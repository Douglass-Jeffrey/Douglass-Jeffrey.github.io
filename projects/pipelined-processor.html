Pipelined RISC-V Processor on an FPGA

Personal project - 2026 - GitHub

Overview

This is a 5-stage, in-order RISC-V (RV32I) processor that I wrote in Verilog and run on the Cyclone II FPGA of an Altera DE1 board. It started as a textbook five-stage pipeline and grew, one verified step at a time, into a processor with full forwarding, a two-bit branch predictor, and an 8 KB instruction cache and 16 KB data cache in front of the board's 512 KB of off-chip SRAM. It runs at 50 MHz and uses every one of the FPGA's 52 block RAMs.

Most of the work went into making sure the design was right rather than adding features. A pipeline can compute the correct answer and still stall when it doesn't need to, and a design that passes simulation can still be built differently by the synthesis tool. Every change is checked against an independent reference model in simulation, and the board's own performance counters are read back over JTAG and compared with a cycle-exact prediction.

Pipeline

The five stages are the classic ones. IF selects the next fetch address and sends it straight into the instruction cache, whose block RAM latches the address and returns the instruction on the next cycle, in ID. ID decodes, reads the register file and predicts branches. EX forwards operands, runs the ALU and resolves branches. MEM accesses the data cache, and WB aligns load data and writes the register file.

Valid bits and the pipeline freeze

Each pipeline register carries a valid bit. A flushed or stalled slot becomes a bubble: its valid bit goes low and its other fields keep whatever stale values they held. That is harmless as long as every side effect (register writes, memory accesses, forwarding, redirects and predictor training) is qualified by the valid bit of the stage that causes it, and that became the main rule of the design.

The board can run the processor at 50 MHz, 25 MHz, about 1.5 Hz, or one cycle per button press. Rather than generating slower clocks, everything runs on the 50 MHz clock and the speed setting drives a clock enable. When the enable is low every pipeline register holds, valid bits included, so the processor simply pauses. This later became the mechanism for cache misses. The pipeline's enable is clk_en && !dc_busy, so a data cache miss freezes the pipeline exactly as a slow clock does, while the caches and the SRAM controller keep running on every edge.

Hazards

Most data hazards are handled without stalling. Results are forwarded from MEM or WB into EX, with MEM taking priority since it holds the younger write. The value forwarded is the final write-back value, which is resolved in EX, so jal and lui forward pc + 4 and the immediate rather than the raw ALU output. The register file writes through, so an instruction in ID sees a value being written back in the same cycle.

The only stall is a load followed immediately by an instruction that uses the loaded value. The interlock compares register numbers only for the operands an instruction actually reads, so immediate bits that happen to look like a register number never cause a false stall. A store directly behind the load that produces its store data doesn't stall at all: when the store reaches MEM the load is already in WB, so the store takes its data from there.

Branch prediction

Branches are predicted in ID by a table of 32 two-bit saturating counters indexed by the PC, and resolved in EX by a dedicated comparator, kept outside the ALU so the compare doesn't wait on the shifter and result mux. JAL is always taken in ID and JALR is resolved in EX. A correctly predicted taken branch costs nothing and a misprediction costs one cycle. On an insertion sort benchmark the predictor cut flushes from 4,519 to 1,568 and the run from 30,841 to 27,892 cycles.

I chose to predict in ID rather than IF. Predicting in IF would put the predictor's lookup on the same path as the redirect from EX into the next fetch address, which was already the longest path in the design. In ID the instruction has been decoded, so the predicted target is just the PC plus the immediate.

Memory system

The FPGA's 52 block RAMs (M4Ks) hold about 26 KB in total, and originally the instruction and data memories lived entirely in them. To make room for larger programs and data I moved main memory to the board's 512 KB SRAM chip and turned the block RAMs into caches. The SRAM is split in half: the low 256 KB holds code and the high 256 KB holds data, so the two sides keep separate address spaces, as the original memories did. Both caches are direct mapped with 16-byte lines, which splits an 18-bit address as follows:

icache, 8 KB512bits 17–13bits 12–4bits 3–0
dcache, 16 KB1,024bits 17–14bits 13–4bits 3–0

Because the index and offset are simply the low address bits, each cache's data array is laid out like a small ordinary memory, and only the tag array decides whether what it returns belongs to the address being accessed.

Data cache

The data cache is write-back and allocates on a store miss, so a store that misses fetches its line first and then writes it. Its tags and valid bits share one RAM, its dirty bits have their own, and its data is split into four byte lanes, each a separate RAM holding one byte of every word. A store enables only the lanes it writes, so byte and halfword stores finish in a single cycle with no read-modify-write.

The tricky part is timing. A load reads the data RAM on its way from MEM to WB, exactly as the original data memory did, so a hit costs nothing extra. A store, however, writes on the edge leaving MEM, so the cache has to know whether it hits before that edge. The tag RAM is therefore addressed with the ALU result while the access is still in EX, a stage early, and the tag compare happens in MEM. A miss raises busy, which freezes the pipeline before the store can write into the wrong line.

Each byte lane is a true dual-port RAM. One port belongs to the pipeline, for loads and stores, and is addressed directly by the EX/MEM pipeline register. The other belongs to the cache controller, for refills and write-backs. The two are never active at the same time, since the controller only works while the pipeline is frozen, but giving the controller its own port keeps the pipeline's address path a plain wire, which mattered for timing.

On a miss the controller reads the victim line's dirty bit, copies a dirty victim out through its port and writes it to SRAM, reads the new line from SRAM, writes it into the lanes one word per cycle, writes the new tag, and finally forces a hit so that the frozen load or store completes. The tag is written last, so a half-written line is never valid. A miss costs about 42 cycles, or about 85 when a dirty line has to be written back first.

The dirty bit is read after the miss is detected rather than early with the tag. A store hit just ahead in the pipeline can be setting that same dirty bit on the same clock edge, and an early read would return the old value. A dirty line would then look clean and be thrown away without being written back.

Instruction cache

The instruction cache is read only. Its tags and instructions are read together, on the edge that latches the next fetch address, and the hit check happens in ID. A miss is handled like a load-use stall: the fetch is held and a bubble goes into EX, while the instructions already in EX, MEM and WB keep going. The line is fetched from the code half of the SRAM in about 45 cycles.

The cache powers up already holding the program from the FPGA's configuration image, with every line marked valid, so a program of up to 8 KB runs without anything having to load the SRAM first. The miss path is fully exercised in simulation by starting with the cache empty and the program in the SRAM model.

SRAM controller and arbiter

The SRAM chip has a 16-bit data bus, so the controller moves a 16-byte cache line as eight 16-bit transfers. Each transfer has a full cycle of setup before the write strobe, a two-cycle strobe and a full cycle of hold after it, and every SRAM pin is driven from a register in the FPGA's I/O cells to keep the skew between pins small. A line takes about 35 cycles, 0.7 µs, or about 23 MB/s. That is roughly an eighth of what the 10 ns chip can do, a margin I chose deliberately for bring-up and plan to cut back.

The two caches share the controller through an arbiter. When both miss at once the data cache goes first, since its miss freezes the whole pipeline while an instruction miss only holds the front end.

Verification

Each test program runs on both the RTL and an independent RV32I reference model written in Python. The runner compares the trace of retired instructions one by one, the final registers and every nonzero word of data memory, read through any dirty cache lines, and for directed tests the exact number of stalls and flushes, so a pipeline that stalls when it doesn't need to still fails.

  • Directed tests cover forwarding, load-use stalls at each distance, control flow, branch prediction with exact flush counts, and cache evictions.
  • Random programs are biased toward short register dependencies and colliding loads and stores. Half of their memory accesses use a base register that jumps between addresses 16 KB apart, so they land on the same cache line with different tags and force dirty evictions.
  • Every test runs in several modes: with the clock enable always high, low every other cycle and random, and with the instruction cache preloaded or empty. The results must not change between modes.
  • A model of the SRAM chip checks its timing rules (setup and hold around the write strobe, access time and bus contention) on every simulation.
  • Unit tests include 50,000 random accesses to the data cache, about 47,000 of them misses and 23,700 dirty write-backs, checked against a byte-level reference memory.

To check that the tests can actually fail, I break the design on purpose. An early round of 14 deliberate bugs was caught 13 times (the survivor turned out to be unreachable), and two deliberately broken caches, one that skipped write-backs and one that never set dirty bits, both failed immediately.

On the board, a simulation twin of the board wrapper predicts all 16 words the board can report: cycle and event counters, results, the final PC and instruction, and miss counts. A script reads the same words over JTAG through In-System Sources and Probes and flags any that differ. The board's switches select any word for the 7-segment display.

Challenges

The board disagreed with the simulation

The first time the insertion sort ran on the board, it reported the wrong checksum, and 34,529 cycles instead of the predicted 30,841, identically at two clock speeds. Since a timing problem would have changed with the clock speed, I suspected the hardware was logically different from the RTL. I exported the post-fit netlist from Quartus and simulated it with Altera's primitive library, and it reproduced the board's numbers digit for digit.

Comparing the netlist's retired instructions with the reference model, the first difference was instruction 13,649, a branch on a value that had just been loaded. These were the first loads the program executes, since everything before them only stores. A loaded value of 0x000000F5 came back as 0xF5000000. Inspecting the netlist showed why: the data memory's block RAMs had only 8 of their 32 write-data inputs connected, and the other 24 tied to ground. Quartus had mis-built the byte-enable RAM my RTL described, without a warning. I rewrote the data memory as four independent byte-lane RAMs, each with its own write enable, so no byte-enable inference is involved, and the same lanes became the data cache's design later. The lesson stuck: passing RTL simulation doesn't prove the hardware, so I check what synthesis actually built.

Bringing up the SRAM

My first SRAM controller passed its testbench, but that testbench treated the SRAM as an ideal memory. I wrote a model of the chip that enforces its timing rules: the address and data must be stable around the write strobe, data is only valid after the access time, and nothing else may drive the bus while the chip does. Against it, the controller produced 238 violations, such as the address changing on the same clock edge as the write strobe. I rewrote it so every transfer has a full setup cycle, a strobe and a full hold cycle, with every pin driven from an I/O-cell register.

Before connecting it to the processor I built a standalone board test that writes every word of the SRAM with a pattern derived from its address, reads it all back, then repeats with every bit inverted. To make sure the test could catch a fault, I ran it in simulation against chip models with a stuck address bit and a stuck data bit, and it flagged both at the expected addresses. On the board it completed over a hundred full passes of all 512 KB with no errors, which settled the pins, the two-way data bus and the timing before the caches existed.

Getting the caches into block RAM

Quartus decides from the Verilog whether a memory becomes block RAM, and when the code doesn't match one of its templates it silently builds the memory out of flip-flops and logic instead. This came up three times.

  • The instruction memory was being built from logic. Nothing writes it, so Quartus treats it as a ROM, and ROMs follow the romstyle attribute rather than the ramstyle I had used.
  • Each data cache lane needs two read/write ports, with a clock enable on the pipeline's port so a freeze holds the load data. I tested several coding styles in small prototype projects and found that Quartus 13 won't infer a true dual-port RAM with any clock enable at all. An earlier experiment that needed a similar RAM had fallen back to over 20,000 logic elements, more than the whole chip. The lanes now instantiate Altera's altsyncram block directly for synthesis, with a behavioural model for simulation.
  • When I placed a multiplexer in front of the data memory's address, Quartus could no longer merge the EX/MEM pipeline register into the block RAM's own address register, and Fmax dropped by about 6 MHz. Every cache RAM is therefore addressed directly by a pipeline register, which is why the cache controller has its own port instead of sharing the pipeline's.

Closing timing after the caches

Adding the caches spread the design across both columns of block RAM on the chip, and Fmax fell to 49.65 MHz, 0.14 ns short of the 20 ns clock period. Every failing path started at the data cache output: load data in WB, forwarded into EX, through the 32-bit branch compare and the next-PC logic, and across the chip into the instruction cache's address registers.

The branch compare arrives last but passed through four levels of next-PC logic. I rewrote the next-PC logic to compute the next PC for both outcomes of the compare and let the compare choose between them in one final mux. The first compile came out slower, at 46.8 MHz, because Quartus had merged the two halves back into one deep function. Marking both halves with a keep attribute stopped that and brought Fmax to 51.0 MHz. The next worst path was the JALR target, which came out of the ALU and so waited on its shifter and result mux even though it only needs rs1 + imm. Giving JALR its own adder, as I had done earlier for the branch comparator, brought the design to 52–54 MHz.

A miss that never finished

One test hung with the clock enable low every other cycle and the instruction cache starting empty. It retired 8 of its 25 instructions while the instruction cache refilled the same line 277 times. The cache's tag RAM is only read on edges where the pipeline moves. At half speed, the edge right after a refill wrote the new tag was often a disabled one, so the controller went back to idle still looking at the old tag, decided it had missed again, and fetched the line again, forever. The fix makes the controller's last state wait for an edge where the pipeline moves, so the tag is re-read before it returns to idle.

Neither condition caused the bug on its own. Tests with an empty cache at full speed passed, and so did tests at half speed with the cache preloaded. Since then the suites run the combinations of cache and clock-enable modes after every cache change.

Results

All three versions retire the same 25,276 instructions with 1,044 load-use stalls. The cycle count adds up exactly: 25,276 instructions, plus 1,044 stalls, plus 1,568 flushes, plus 16 cache misses of 42 cycles each, comes to 28,560, with a few more cycles to fill the pipeline. The 16 misses are compulsory, one per line of the array, and cost 2.4% of the run. Before the caches were added, the board matched the simulation's prediction on every counter.

What I'd do next

  • A program loader over UART or JTAG, and a single shared address space for code and data, so programs can use all 512 KB instead of the 8 KB preloaded with the FPGA image.
  • Faster misses. The SRAM controller uses a fraction of the chip's speed, and a write-back buffer would let a dirty miss fetch its new line before writing the old one back, roughly halving its cost.
  • Register load data in MEM to remove every critical path that starts at the data cache, which together with a PLL should allow 65–70 MHz.
  • CSRs, traps and interrupts.

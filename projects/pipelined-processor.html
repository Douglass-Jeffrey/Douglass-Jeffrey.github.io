Pipelined RISC-V Processor on an FPGA

Personal project - 2026 - GitHub

Overview

A 5-stage, in-order RISC-V (RV32I) processor written in Verilog. It runs at 50 MHz on the Cyclone II FPGA of an Altera DE1 board, with an 8 KB instruction cache and a 16 KB data cache in front of the board's 512 KB SRAM. Every design change is checked against a Python reference model with directed, random and unit testbenches before it goes on the board.

ISARV32I (no CSRs, traps or interrupts)
PipelineIF, ID, EX, MEM, WB, in order
Clock50 MHz, Fmax about 52–54 MHz
Caches8 KB icache + 16 KB dcache, direct mapped, 16-byte lines
FPGA use~6,300 of 18,752 logic elements, all 52 M4K RAM blocks

Pipeline and hazards

Most data hazards are handled without stalling. Results are forwarded from MEM or WB straight into EX, and the register file writes through so an instruction in ID sees a value being written back in the same cycle. The only stall is a load followed immediately by an instruction that uses the loaded value.

HazardHandled byCost
ALU result used by the next instructionForwarding from MEM or WB into EX0 cycles
Load result used by the next instructionLoad-use interlock1 cycle
Store right after the load that produces its dataLoad-to-store forwarding in MEM0 cycles
Branch mispredict or jalrRedirect from EX1 cycle

Branches are predicted in ID with 32 two-bit saturating counters, so a correctly predicted taken branch costs nothing. Predicting in ID instead of IF keeps the predictor off the critical path into the next fetch address.

Memory system

  • icache: 8 KB, direct mapped, read only. A miss stalls the front of the pipeline while the instructions already past it keep going.
  • dcache: 16 KB, direct mapped, write-back, and allocates on a store miss. Each byte of a word lives in its own RAM lane, so byte and halfword stores finish in one cycle with no read-modify-write.
  • Memory arbiter: picks between icache and dcache requests and gives the dcache priority, since its misses freeze the whole pipeline.
  • SRAM controller: moves a 16-byte cache line as eight 16-bit transfers to the board's asynchronous SRAM.

A dcache miss costs about 42 cycles, or about 85 if a dirty line has to be written back first.

Timing

The critical path runs from load data leaving the dcache, through forwarding and the branch comparator, to the next fetch address. Adding the caches pushed it past the 20 ns clock period. Two changes brought it back under: computing the next PC for both branch outcomes in parallel and choosing between them at the last mux, and giving jalr its own adder instead of waiting on the ALU.

Verification

Each test program runs on both the RTL and an independent RV32I reference model written in Python. The runner compares the trace of retired instructions one by one, the final registers and memory, and the exact number of stalls and flushes, so a pipeline that stalls when it doesn't need to still fails. The tests include:

  • Directed tests for forwarding, load-use stalls at each distance, control flow, branch prediction and cache evictions.
  • Random programs biased toward short register dependencies and loads and stores that collide in the cache.
  • Unit tests, including 50,000 random accesses to the dcache checked against a reference memory.
  • A model of the SRAM chip that checks its timing rules on every simulation.

What's next

  • A program loader over UART or JTAG, so programs aren't limited to the 8 KB preloaded with the FPGA image.
  • One shared address space for code and data.
  • Registering load data in MEM to shorten the critical path, which should allow 65–70 MHz.
  • Faster miss handling, such as a write-back buffer.
